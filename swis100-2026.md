### First test of "native" linopy custom constraint

Another bit of an unnecessary rabbit hole. We use:

	m = n.create_model()

to get access to the `model` object in order to add (custom)
constraints before solving. BUT note that the "shortcut" call:

	n.optimize()

appears to *always* reconstruct `n.model`, blowing away any
modified version in the process. So must not use it, if using
custom constraints. Instead, must use:

	n.optimize.solve_model()
	
But with that, first attempt at custom constraint (forcing IC
`p_nom` to be the same in both directions) seems to work
perfectly. Yay.

## TODO: major refactor of `run_config` design?

Current design is very clunk and clumsy to maintain or add
functionality. Is there a more "pypsonic" approach? As in:
populate a df "directly" with parameters required for each SWIS
subsystem? Better: have SWIS provide a function to construct a
df, pre-populated with all the required pypsa components and
"relevant" parameters, so that user need only modify things that
need to change for a specific run? This could come with the
techno-economic parameters also already in place, so they can
still be modified on a run-by-run basis.

There may be a conceptual catch here, in that SWIS "subsystems"
don't map one-to-one onto pypsa components (multiple components may be
required to implement a subsystem); and (separately?) SWIS-level
run config parameters may not map directly to individual
pypsa-level component parameters. But yet they feel tantalisingly
close? But yes, probably need to accept that there will be a SWIS
parameter "abstraction layer" that may be reminiscent of pure
pypsa-component configuration, but is nonetheless different and
distinct. So the flow should become something like:

	swis_config = swis.create_config()
	# Includes techno-economic parameters!
	# Inspect/modify as required, and then ...
	network = swis.create_network(swis_config)
	# Returns pypsa network
	# Inspect/modify if desired on run-by-run basis (but avoid in general?)
	model = swis.network.create_model()
	# Returns pypsa/pinopy model, *just in case* there is a need for
	# run-specific tweaking of linopy-level LP constaints.
	# Inspect/modify if desired on run-by-run basis (but avoid in
	# general?)
	network.optimize.solve_model()

Not quite sure how this translates into the batch-run SWIS use
case; but presumably the `swis_config` object that takes the
place of existing `run_config` above may map onto a row (or a
sheet?) of a batch run spreadsheet?

## TODO: tech portfolio

### methanol?

My conjecture is that, in the IE case, synthetic methanol (with
carbon cycling) is going to be a more "practical" option for
ULDES than H2 (based on Tom Brown work especially). It's also
much more suitable for "incremental" deployment; and has
worthwhile prospects for learning effects to drive costs down
(?). So I would definitely like to have it included in the 100%
zero carbon portfolio...

Of course we already have a synthetic liquid fuel subsystem to
service aviation; OK, methanol is not kerosene, so would need to
refine this a little. But it does seem like having a pathway back
to electricity (OCGT/CCGT) from stored liquid efuel could be configured in
parallel with the pathway from H2? But need to allow for the CO2
release from any hydrocarbon efuel (SNG or e-methanol) in a link
from such a fuel store to a "carbon free fuel" bus that feeds
OCGT and CCGT (currently labelled H2 of course). The point is to
trade off the extra losses in going to a hydrocarbon fuel vs the
potentially much (much!) cheaper cost of storage? 

### Heat networks, waste heat, heat storage?
