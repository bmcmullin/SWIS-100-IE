### Test own basic example: `constrain-gen.ipynb'

[constrain-gen.ipynb](https://groups.google.com/g/pypsa/c/HghmWRo94SM/m/zdKpY_vaBAAJ)

This was a toy example I generated (for Mohammed Riadh Habour) to
illustrate the evolving `pypsa` optimize API, and specifically
migrating custom constraints (as needed for SWIS!). 

	IES.lopf(pyomo=False)

	AttributeError: 'Network' object has no attribute 'lopf'

So ... `n.lopf()` no longer exists. It looks like this is the
"drop in" replacement:

	IES.optimize()

which does run to completion (nicely defaulting now to `Highs` solver).

But ... attempting to add back the one example custom
constraint:

	model = IES.optimize.create_model()
	lhs = model.variables["Generator-p"].sel(Generator='Oil_generator').sum()

now throws:

	KeyError: "'Generator' is not a valid dimension or coordinate
		for Dataset with dimensions 
		FrozenMappingWarningOnValuesAccess({'snapshot': 8760,
		'name': 2})"

Some rather ad hoc experimenting suggests this change:

	lhs = model.variables["Generator-p"].sel(name='Oil_generator').sum()
	
which now allows:

	IES.optimize.solve_model()

to run to completion, with what appears to be sensible
results. Yay.

### First test of "native" linopy custom constraint

Another bit of an unnecessary rabbit hole. We use:

	m = n.create_model()

to get access to the `model` object in order to add (custom)
constraints before solving. BUT note that the "shortcut" call:

	n.optimize()

appears to *always* reconstruct `n.model`, blowing away any
modified version in the process. So must not use it, if using
custom constraints. Instead, must use:

	n.optimize.solve_model()
	
But with that, first attempt at custom constraint (forcing IC
`p_nom` to be the same in both directions) seems to work
perfectly. Yay.
